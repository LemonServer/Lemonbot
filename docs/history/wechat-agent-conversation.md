## 长期记忆（2026-10-10 启用）

本机私有运行配置 `[wechat_agent] memory_enabled = true`；公开模板默认为 false。
切换开关后按白名单手册暂停、等待在途任务完成、重启并显式恢复。关闭开关保留已存记忆。

每条回复精确确认后，利用同一模型和预算追加至多一次 JSON 整理请求，提取重要事实、
稳定偏好、明确承诺；上下文被裁剪或达到 24 条消息时请求滚动摘要。
来源消息 ID、模型、提示版本、可信度和时间随记忆保存到现有数据库。
引用内容不自动归为当前发言者的偏好；记录作为可修订材料而非绝对事实。
当前回复生成时尚未执行此次整理，不能保证口头“已记住”意味着长期记录已经成功保存。

记忆沿用 context_scope：私聊联系人独立，群按群＋成员独立，群与私聊不共享。
查询按当前文字进行 SQLite FTS/词项检索，额外召回同范围的有效承诺，最多十项传入
上下文选择器；不是向量检索，不保证换一种说法也必然召回。记忆标为不可信资料，
与近期对话一起受 8,192 tokens 总上限和 512 输出预留约束。

整理安排在确认送达之后，使用处理门禁，不允许读取重入；当前回复不等待整理完成才发送，
整理期间下一条消息可能等待。超时、预算不足或记忆库失败时忽略本次整理并记录固定审计原因，
不重试模型，不改变已经确认的回执；UNKNOWN 回复不提取、不重发。
暂停时不开始新的整理。进程在 ACK 后、整理完成前中断可能漏一次提取，不自动补付费请求。
不扫描全量历史；下一条成功交互的整理会使用当前隔离范围的近期已确认记录。

确认后提取、UNKNOWN 排除、成员隔离、数据库重开检索通过自动化验证。
本机开关已部署；真实新交互的记忆提取/召回需从 `memory.derive` 审计与后续实际回答确认，
不以开关启用代替端到端验收。

## 导航、发送与上下文

读取不依赖前台；发送串行执行：核验账号与绑定内部 ID → 验证前台（目标不在前台才打开会话）→ 唯一名称与前台语义标题复核 → 一次 POST →
精确确认唯一新 self 消息。导航失败暂停对应会话；身份变化、缺失或 UNKNOWN 暂停整个通道。
历史同文消息允许存在，新消息仍按不同 ID 处理。歧义和超时不自动重发；暂停不会因程序重启解除。
群上下文按群＋成员隔离，私聊按联系人隔离；只有确认送达的助手回复进入后续上下文。
非触发群消息、自发消息、非白名单消息不调用模型，也不进入模型上下文。模型失败不重复调用。

采用 DeepSeek Flash，8,192 输入上下文、512 输出 tokens、2,000 字符回复上限。
全天被动响应，保留原发送限流，每日 5 元、每月 100 元。价格与官方余额接口见 [计费说明](../reference/models/deepseek-pricing.md)。

## 新 @ 再次失败后的直接定位（北京时间 20:18–20:34）

用户发送两次新验收真 @，未收到回复。只读界面树在已核验的 testing 前台识别到新验收文本，
用户确认在同一群看到自发诊断消息；API 中却没有新验收文本。这次排除了仅为历史基线的解释，
前述“对端消息早于基线”仅是当时 API 可见结果，不能反推对端没有发送。

现场 WAL 对照：

| 读取方式 | 目标消息数 | 结论 |
|---|---:|---|
| 实时普通 SQLCipher 只读 | 43 | 未见新验收消息 |
| 仅在受限临时加密副本合入提交页 | 44 | 新提交页能改变目标群读视图，仅作取证 |

捕获时 WAL 头部校验正确、当前盐匹配的前六帧存在提交标记，但标准累计帧校验失败。
独立按上一帧记录的校验值核算，后续五帧密文校验可通过，异常集中于首帧与头部的校验衔接；
SHM 同时报告 mxFrame=0。标准读取没有纳入这批提交，符合
[SQLite 的 WAL 有效帧与读算法](https://www.sqlite.org/fileformat2.html#walformat)。

**已定位直接故障机制，尚未完成修复：**新消息所在 WAL 不能被当前标准读取作为有效提交纳入。
首帧/头部异常由客户端、并发读写还是其他环节产生，仍未确认。随后 WAL 发生 epoch 重置，
旧尾帧与当前盐不匹配是正常回收状态，不能把每个旧尾帧都记作损坏。
外部 SQLCipher 为 4.6.1/SQLite 3.46.1；未找到可直接调用的微信加密数据库导出 API。
不能据此断言整个加密格式不同，也不能将未经验证的覆盖副本用作生产数据源。

新增只读审计脚本 [agent_wechat_wal_audit.py](../../scripts/agent_wechat_wal_audit.py)，按官方格式
区分头部校验失败、当前帧校验失败、旧 epoch 尾帧和未提交尾部；不解密、不改原文件、
不输出路径、页面内容或账号。5 项真实 SQLite WAL/故障注入检查通过。

通道已重新持久暂停，无新验收入站、无新模型调用、无自动回复；旧 UNKNOWN 一条保留不重发。
下一步限定为验证首帧/头部异常的产生点，优先隔离实时 SQLCipher 读对共享 WAL/SHM 的影响，
随后才考虑受校验保护的容器内快照读取。不重置账号数据、不忽略校验、不重启登录排列组合。

## 根因与修复完成（北京时间 21:05）

首帧校验逆推得到初值 (0,0)，后续密文帧逐帧累计校验通过；现场微信 WAL 的帧链从零开始，
而标准 SQLite 从头部校验值开始。停掉自有桥、只发送一条新的自发诊断的隔离对照中，
相同标准首帧校验失败仍出现；尚不能将格式差异的产生归因于自有桥。固定运行服务二进制
存在 immutable=1 字面量，但这不能代替全路径行为证明。

新增 [严格快照读取](../../scripts/agent_wechat_wal_snapshot.py)：验证头部、当前 epoch 盐、

## 延迟优化运行说明（2026-10-10）

认证内部 `POST /read-cycle` 一次增量读取两个绑定会话，同库只捕获一次严格快照。
每会话固定快照内最多十页，每页一百条，下一锚点保留最新一页标识。
来源变化最多三次只读重试；身份缺失、损坏帧、账号变化和锚点丢失仍暂停。
入库后立即唤醒处理；待处理入站和待确认 outbox 优先，忙碌时只合并通知。
同一阶段完整核验后已在目标前台则省去导航，不跨阶段缓存认证。

自动报告（仅性能验收合成指令，不输出正文、账号或会话标识）：

```bash
uv run --locked python scripts/wechat_latency_report.py
journalctl --user -u lemonbot-wechat-conversation.service --since today --grep="latency stage="
```

日志以单调时钟记录锁等待、通知到读取、快照、入库、任务领取、策略、模型和 HTTP 阶段。
数据库报告的端到端时长使用带时区的消息时间和回执时间，包含不同进程时钟误差。
