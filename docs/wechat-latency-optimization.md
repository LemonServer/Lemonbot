# 微信收发延迟优化（2026-10-10）

状态：六条指定收发均确认。代码优化后同机中位数 37.14 秒，未达 35 秒目标；
扩容并重启后两条中位数 13.202 秒，达到 25 秒目标。服务保持运行。
日常双会话功能已有实机验收，本轮性能收益必须由新收发测量确认。

## 修改前基线

代码 `42d64f8`，2 vCPU、约 4 GiB RAM，存在 CPU 竞争与换页。
最近 12 条确认消息的各段中位数如下（各段中位数不能直接相加）：

| 阶段 | 秒 |
|---|---:|
| 消息至持久化 | 16.48 |
| 持久化至 outbox 建立 | 16.26 |
| outbox 排队 | 0.66 |
| 派发至确认 | 28.50 |
| 总耗时 | 62.67 |
| 实际模型请求相关预算区间 | 1.02 |

此前“持久化至 outbox”包含调度等待，不能当作模型请求时间。
机器采样表明存在竞争，但没有硬件对照前不能量化机器与代码各自贡献。

## 分阶段实现

| 提交 | 变化 |
|---|---|
| `e489dff` | 单调时钟测量入库、领取、策略、模型、HTTP 阶段及锁等待 |
| `f3c3257` | 认证内部 `POST /read-cycle`，同库共用严格快照，两会话批量增量读取 |
| `89a9850` | 入库唤醒处理，待处理入站和待确认 outbox 优先于下一轮读取 |
| `fbf5afc` | 已验证目标前台时省去打开操作，保持完整身份与唯一回执校验 |

每会话最多十页、每页一百条，锚点最多一百条；读取期间到达的新消息留给下一轮通知。
账号在周期开始和结束核验；损坏帧不跳过，来源变化最多三次只读重试。
旧 `/messages` 保留给回执与诊断，canary 路径兼容；Connector 和数据库 schema 不变。
处理与发送期间不接收重入，通知合并，目标轮转避免私聊饥饿。
发送仍一次 POST；超时、歧义或中断进入 UNKNOWN，禁止自动重发。
发送前后仍核验账号、绑定 ID、唯一名称与前台目标，不跨阶段缓存认证。

- 新覆盖共享快照、分页边界、锚点丢失、账号变化、通知积累、任务优先、前台复用和导航。
  既有真 @、白名单、UNKNOWN、暂停、急停、限流、持久上下文测试继续通过。

  均核验两个目标、返回零条历史事件，无暂停原因；该结果不计作端到端收发测量。

部署前暂停并确认活动入站和 outbox 均为零。仅更新自有桥、重启桥及 runtime；

日志只记录固定阶段名和耗时；不输出正文、凭据、原始标识或完整 API 路径。

## 六条实机测量

同一对端账号依次发送，每次收到回复后再发下一条；群须通过成员选择真正 @ 本机。
不可重发或人工补发机器人回复，按既有限流执行。

| 阶段 | 会话 | 指令 |
|---|---|---|
| 同机 | 群 | 性能验收同机群一：只回复“好”。 |
| 同机 | 私聊 | 性能验收同机私一：只回复“好”。 |
| 同机 | 群 | 性能验收同机群二：只回复“好”。 |
| 同机 | 私聊 | 性能验收同机私二：只回复“好”。 |
| 扩容 | 群 | 性能验收扩容群：只回复“好”。 |
| 扩容 | 私聊 | 性能验收扩容私：只回复“好”。 |

自动报告：`uv run --locked python scripts/wechat_latency_report.py`。
报告只选择合成性能指令，输出阶段、会话类别、尝试次数、回执状态与各段耗时。
单调时钟日志定位内部等待；端到端使用带时区的消息和回执时间，保留原始小样本。
同机 ≤35 秒、扩容 ≤25 秒是目标；同机未达标、扩容后达标，不宣称少量样本有长期统计意义。

## 扩容、恢复与回退

同机验收通过后，确认无在途模型或发送任务，持久暂停，再由用户关闭虚拟机，
在虚拟化软件中调整为 4 vCPU、8 GiB RAM。保持代码、镜像、微信版本、原卷和模型不变。
启动后先核验资源，按 [运行手册](wechat-agent-conversation.md) 恢复固定容器、自有桥与服务，
核验登录及两个绑定，显式恢复建立新基线，再发最后两条。宿主不能提供资源时标记硬件对照待完成。

漏消息、错会话、重复发送或暂停失效时立即持久暂停，保留新 UNKNOWN，不自动重发。
记录故障阶段后回退最近优化提交，更新桥与 runtime 前再次确认没有在途任务。
回退采用版本控制逆向提交，不删除数据库、原卷或证据，不清除暂停来绕过核验。
验收后保持服务运行，不追加观察窗口，不放宽预算或限流。

## 扩容恢复（2026-10-10，北京时间）

核验 4 vCPU、约 7.7 GiB 系统内存，启动时 swap 使用为零。
固定容器首次启动 exit=1，日志停在音频初始化，后续启动恢复；音频故障的底层原因未证实。
检测到音频进程存活时拒绝清理，未删除任何音频或账号文件。
镜像、数据卷、产品代码、模型及限流保持不变；初次 API 返回已登录，随后用户确认 noVNC 实际未登录；该 API 结果不足以证明登录恢复。

宿主重启后两个 transient user units 消失：桥 helper 在停止不存在的单位时退出，
容器内桥已安装，但宿主转发尚未启动。已手动重建转发和 runtime，保留 ManualPause，
显式恢复成功，两个目标无暂停原因，活动发送为空，旧 UNKNOWN 一条。
这是人工恢复记录，不能宣称宿主开机自动恢复。最后两条扩容测试结果见下文。

## 登录状态更正（2026-10-10）

用户检查 noVNC 后报告未登录并手动完成登录。此前 API 返回 logged_in 及聊天列表存在，
不能据此宣称可见客户端已登录或无需人工登录。此时两个服务仍 active，
运行通道因 MessageSnapshotUnavailable 持久暂停，队列为空、旧 UNKNOWN 一条。
手动登录后再次读取 auth 与聊天列表正常，显式恢复成功，重新核验绑定并建立基线。
状态恢复不计作收发通过；随后两条新消息闭环单独确认。

手动登录后的实际双会话只读基线周期为 1.226 秒，账号核验通过、两个目标均无错误，
返回零条历史事件；随后状态仍未暂停、队列为空。该只读测量不代表完整收发耗时。

## 最终扩容对照结果（北京时间 12:26）

用户确认收到且明显变快；两条均 acknowledged、attempts=1。

| 会话 | 收取 | 入库至模型开始 | 模型及提交 | 派发至确认 | 总耗时（秒） |
|---|---:|---:|---:|---:|---:|
| 群 | 1.865 | 0.045 | 0.713 | 9.820 | 13.037 |
| 私聊 | 1.838 | 0.024 | 0.701 | 10.280 | 13.367 |

扩容后总耗时中位数 **13.202 秒**，低于 25 秒目标；较同机 37.1405 秒低约 64.45%，
较历史 62.67 秒低约 78.93%。样本分别为历史十二条、同机四条、扩容两条；
报告分阶段中位数，不将不同配置下六条混合中位数作为最终性能指标。

单调时钟模型请求中位数 0.697 秒，认证 0.435 秒、前台语义读取 0.363 秒、
导航 2.234 秒、发送 POST 2.695 秒。主要剩余耗时仍在导航、发送与回执守卫，
本轮不修改上游执行计划。扩容伴随宿主重启、换页清除和后台负载变化，
以上不能单独归因于 CPU 或内存，也不代表复杂模型回复的长期耗时。

最终状态未暂停、两个目标无暂停原因、队列为空，旧 UNKNOWN 一条、无新增 UNKNOWN。
